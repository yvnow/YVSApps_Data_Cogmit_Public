# TASK: Fix Cogmit Markdown Rendering — Diagnose First, Then Implement

## Objective

Fix Markdown rendering in Cogmit so that RootCog content renders with correct semantic structure and readable styling, comparable in structure to GitHub's Markdown preview.

The application currently supports six Markdown parsers:

1. `markdown-it`
2. `marked`
3. `remark` using `remark-parse`, `remark-rehype`, and `rehype-stringify`
4. `micromark`
5. `showdown`
6. `commonmark.js`

The six parsers must remain available. Do not remove or replace them.

The existing View button and `view1`–`view6` switching behavior must remain functional.

## 1. Mandatory Repository Inspection

Before editing, inspect the actual repository and identify:

- The RootCog reading route and page component.
- The six parser implementations and their dependencies.
- The function that receives each parser's returned HTML.
- The exact DOM insertion mechanism.
- Any HTML sanitizer and its configuration.
- All CSS affecting the Markdown reader, including global resets and component-level selectors.
- Existing GFM extension configuration.
- Existing tests and build commands.

Do not assume filenames, frameworks, class names, or component structures. Find them in the repository.

Trace the complete pipeline:

`Canonical Markdown source → parser → generated HTML → sanitizer (if present) → DOM insertion → CSS → visible output`

Do not change code until the relevant pipeline has been identified.

## 2. Diagnose the Actual Failure

Use the same canonical Markdown input for all six parsers.

For each parser, inspect its generated HTML for these constructs:

- Heading: `<h1>` or `<h2>`
- Paragraph: `<p>`
- Nested list: `<ul>`, `<ol>`, and nested `<li>`
- Table: `<table>`, `<thead>`, `<tbody>`, `<tr>`, `<th>`, and `<td>`
- Blockquote: `<blockquote>`
- Inline code: `<code>`
- Fenced code: `<pre>` and `<code>`
- Link: `<a href="...">`
- Strikethrough: `<del>` or `<s>`
- Task-list elements, where supported.

Compare the output at these boundaries:

A. Parser output before sanitization.

B. Sanitized output after sanitization.

C. DOM structure after insertion.

D. Computed styles and final visible rendering.

Use the browser's DOM inspection or existing development tools where available. Add temporary diagnostic logging only if needed, and remove unnecessary debug logging before completion.

Determine the actual failure layer. Do not assume CSS is responsible without checking the HTML and DOM.

### Diagnostic decision rules

- If the parser output lacks the expected semantic elements, investigate parser configuration and supported syntax.
- If parser output is correct but sanitized output loses required elements or attributes, investigate the sanitizer configuration.
- If sanitized output is correct but the DOM contains literal HTML text instead of elements, fix the insertion mechanism.
- If the DOM contains correct elements but they appear as unformatted text, investigate CSS resets, selector specificity, and computed styles.
- If only certain Markdown constructs fail, identify their parser-extension requirements.

Report the findings briefly in the final implementation report.

## 3. Preserve the Existing Architecture

The canonical RootCog Markdown source must remain unchanged during rendering.

Do not:

- Write generated HTML back to Markdown files.
- Create separate content copies for the six parsers.
- Change RootCog identity, routes, metadata, or storage hierarchy.
- Change GitHub persistence or commit behavior.
- Introduce a database, cache, or storage layer.
- Add autosave, drafts, background workers, analytics, or unrelated features.
- Rewrite the parser architecture merely to make all six render identically.
- Introduce a new Markdown editor.
- Redesign the Cogmit UI.

Make the smallest targeted changes that correct the identified failures.

## 5. Align Parser Syntax Support Where Possible

Preserve all six parser implementations, but configure their supported extensions explicitly where appropriate.

Required baseline:

- Headings and paragraphs.
- Ordered and unordered lists.
- Nested lists.
- Fenced code blocks.
- Inline formatting.
- Links and reference links.
- Tables where the parser supports a suitable extension.
- Task lists where supported.
- Strikethrough where supported.
- Raw HTML handling consistent with the existing security policy.

For micromark, enable GFM extensions using the appropriate installed packages if they are absent and compatible with the existing version:

```typescript
import { micromark } from "micromark";
import { gfm, gfmHtml } from "micromark-extension-gfm";

const html = micromark(md, {
  extensions: [gfm()],
  htmlExtensions: [gfmHtml()],
});
```

Before applying this example, verify the installed package versions and the project's existing import conventions. Do not duplicate dependencies unnecessarily.

For remark, inspect the existing unified pipeline. Add the appropriate GFM plugin, such as `remark-gfm`, if needed and compatible with the installed versions.

For markdown-it, Marked, Showdown, and commonmark.js, use their supported configuration mechanisms only where appropriate.

Do not claim that all six parsers support every extension. If a feature cannot be supported by a parser without introducing a disproportionate compatibility layer, document the limitation.

Do not modify the canonical Markdown content to compensate for a parser limitation.

## 6. HTML Safety and DOM Insertion

Inspect the current sanitization and insertion mechanism before changing it.

Requirements:

- Treat Markdown content as untrusted input.
- Preserve legitimate generated Markdown elements.
- Sanitize unsafe HTML before inserting it into the DOM.
- Do not bypass the existing sanitizer to make formatting work.
- Do not insert generated HTML as plain text when the reader expects rendered markup.
- Preserve safe links while restricting dangerous URL schemes.
- Prevent script execution, event-handler injection, and other HTML injection.
- Ensure the sanitizer allows only the necessary safe elements and attributes.

If DOM insertion is already correct, do not rewrite it.

If the sanitizer is stripping legitimate Markdown elements, correct its allowlist and configuration narrowly. Never solve that problem by disabling sanitization.

## 9. Acceptance Criteria

The implementation is complete only when:

1. All six views remain accessible through the existing View button.
2. Each view uses its actual parser.
3. The canonical Markdown source remains unchanged.
4. Semantic headings have a visible hierarchy.
5. Nested lists have visible markers and indentation.
6. Paragraphs have readable spacing.
7. Tables have clear cell boundaries and usable overflow behavior.
8. Inline code and fenced code blocks are visually distinct.
9. The blockquote has a visible quotation treatment.
10. Supported GFM constructs render correctly.
11. Parser-specific extension limitations are documented.
12. Sanitization does not unnecessarily remove legitimate Markdown structure.
13. Unsafe HTML cannot execute.
14. Existing Cogmit controls, routes, themes, and persistence behavior remain unchanged.
15. Relevant tests, linting, and build checks pass.
